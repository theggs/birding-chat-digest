# 审稿（可选）

写作规则能防住“系统性”的问题，但每次运行仍会有随机偏差：漏掉一条鸟讯或纠正、把不同论点合成一条、把问句写成判断、把类别写成具体鸟种、内容放错节。这类问题靠继续加规则压不住，规则越加越长还会互相牵制。更有效的做法是在发布前由**另一个 Agent** 对照原始消息审一遍。

同一个模型审自己的稿子，通常看不出自己的问题，所以审稿人应当是另一个 Agent，最好是能力更强的模型。审稿人需要读取原始消息，只交给已获授权、可以接触这些聊天记录的 Agent。

## 流程

顺序固定为：初稿 → 审稿 → 修正 → 生成长图 → 归档终稿 → 发布。

1. **初稿（写作者）**：完成完整报告后，先不生成长图、不归档、不发布。把初稿交给审稿人，同时注明本次运行的 `index.json` 路径。每次运行使用独立的取数目录（例如目录名用运行时间加任务 ID 或随机后缀），保证审稿人对照的正是初稿所用的那份数据。
2. **审稿（审稿人）**：对照原始消息只提意见，不修改文件，不发布终稿。按下面的清单逐项检查。
3. **修正与发布（写作者）**：逐条核对意见和原始消息。接受的照改；不接受的说明理由，并引用写作规则或原文。修正后再生成长图、归档终稿、发布终稿。

审稿意见和不接受的理由只留在内部审稿记录中（只有获授权人员可见的任务评论或日志），不写进报告或长图。终稿末尾最多附一行“审稿处理：接受 N 条；不接受 M 条”。

在定时任务里，可以用 Agent 平台的“@提及”或任务交接机制串起这三步；每一步都是一次独立运行，不需要某一步一直等待。

## 审稿清单

对照本期原始消息（统计区间以 `index.json` 的 `window_start` 至 `window_end` 为准），只查以下五类问题：

1. **曲解或错误归属**：问句写成判断；补写原文没有的因果或过程；把话安到别人头上；原话只说类别（“鹤”“隼”“鸭”）却写成具体鸟种。
2. **漏项**：漏掉的鸟讯（包括“没找到”“已离开”和辨认纠正）、活动召集、有实质内容的讨论议题。
3. **不同论点被合成一条。**
4. **组织不符合所选风格**：按该风格的规则检查。分类简报：某地点有 3 条及以上条目却放进“其他地点”，内容放错类型，同一议题被拆成多节。时间线回顾允许同一话题在不同时间段再次出现，不按此判错。
5. **段末状态句**：“仍属推测”“未形成一致”“这是其立场”之类对讨论状态的判断。

## 审稿边界

- 意见必须符合所选风格的写作规则（例如分类简报的“其他话题”每个一句）；各风格都适用的：单纯的询问不单列，种类和地点都不明的零星反馈不补。
- 不改写文风，不扩写。补回漏掉的鸟讯、纠正、活动召集和有实质内容的议题不受篇幅限制；其他建议新增的内容合计不超过初稿篇幅的 15%。
- 每条意见写明：
  - 改错：报告原句、对应原始消息的时间和发言者、建议改成什么；
  - 补漏：应插入的节、对应原始消息的时间和发言者、建议补写的内容。
- 没有问题时写“无意见”。
